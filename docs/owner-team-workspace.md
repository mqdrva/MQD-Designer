# Owner Team / Brand workspace

Entry: `/team-setup.html?ownerWorkspace=1`, also linked from Owner Orders and Team service management. Requires the existing approved MQD administrator account and authenticator verification. No new account roles, credentials, gallery or checkout.

## Using it

1. Choose Team or Brand pilot. Enter the name and permanent link name. Private organizer email/phone can be left blank while preparing the review and added later; public organizer signup still requires contact details. Add a private placement request/reference if needed. Nothing is emailed by this workspace.
2. Choose flexible fixed-logo editing or strict master editing. Upload the original logo once (PNG/JPEG/WebP, up to 15 MiB); the page preview may be smaller, but the garment original stays unchanged.
3. Flexible mode: select 2D, 3D, or both and set each selected garment's logo to **Fixed**. Use only supported placement presets/dimensions. Members can add artwork and backgrounds around the fixed logo. This is the existing fixed-logo designer, not a granular background/artwork permission system.
4. Strict mode: choose 3D only and enable the garments you want members to see. Each garment has its own separately saved master. Save the owner draft; use **Open garment designer** for its existing owner studio. Its direct `/teams/pilot/3d?setupPreview=1&ownerWorkspace=<workspace UUID>&garment=<product ID>` link loads the private saved setup from the server, with owner sign-in/MFA when needed. A loading screen stays visible until the saved original artwork is ready. Select a layer and drag it on the existing print-zone canvas, use corner handles or the Size slider, and inspect the live 3D garment. Upload with Add Image; only the existing garment zones and safe-area guides apply. The studio includes Customer layer permissions: images stay customer-locked while the owner edits them; for each name select editable text and enable movement. Newly added/replacement layers start locked and need explicit permissions. **Save owner master draft** saves artwork, placements and permissions together without publishing. After a confirmed save the studio returns to this same owner setup, which verifies the saved revision against server data and displays a receipt. Conflicts keep the canvas open. If further edits occur while saving, the saved snapshot is confirmed but the editor stays open with those newer edits still unsaved. Optional backup downloads are never a prerequisite. Optionally allow each designated text field to move within its existing zone and allow one solid whole-garment color. All logos, other artwork, text styling and undeclared positions stay locked. The twelve color presets and custom picker change only the allowed garment backgrounds.
5. Use **Preview member page privately** to try the saved draft without publishing. This requires owner MFA and changes only a temporary independent copy. Permitted names can be dragged on the print-zone canvas as well as positioned with their movement sliders; styling, size, rotation and logo movement stay protected. Private preview downloads/reopening are disabled because no purchased version exists yet. Save/reopen the owner draft as needed. Setup and master changes stay private until **Publish design review link** is clicked. That one explicit action creates an immutable version from the last saved master, then updates the saved setup snapshot at the same customer URL. The server checks the expected master version before updating that snapshot. A failure cannot be treated as successful publication; reopen setup to check before retrying. Fresh visits/new designs receive the explicitly published version; active customer sessions are not forcibly reloaded, and older personalized copies and paid orders retain their exact version. Team API responses use `Cache-Control: no-store`. Share the resulting normal `/teams/<slug>` customer URL yourself. It is viewable by anyone with the URL, grants no editor/admin rights, and supports independent member copies. Unpublish removes public access.
6. The link is design review only. No checkout, subscription, price promise, payout, email or invitation is created. Existing paid Teams continue their established billing/order workflow. Owner-created pilots do not silently acquire that billing workflow. Brand commercial terms and a commercial activation path for owner-created drafts remain a separate decision.
7. Paid orders already placed through the normal Teams service remain in Team service management with their purchased master versions and full production ZIPs. A review copy's **Save my design** ZIP is an unpaid design package, not a paid production order.

Organizer private links can manage their existing billing/requests but cannot save/load/publish masters. Owner-only authoring is enforced by the server using administrator app metadata plus existing MFA.

## Storage and safety

Uses existing private business rows for owner drafts and explicit published shop snapshots, existing Team accounts for association, and existing immutable master versions. Revision-conditional writes reject stale edits. A recoverable account-create step never exposes an incomplete draft publicly and never overwrites an existing account, order or payment. Organizer contact and private request/reference fields are omitted from member responses. Additional garment drafts use an additive private table and service-only save function; public and signed-in customer roles have no access.

## Save conflicts and local recovery

The studio shows an in-flight save message and the saved revision. An out-of-date revision returns HTTP 409 with `master_revision_conflict`; it never force-overwrites another saved draft. The current canvas stays unchanged and a separate-tab link opens the newer saved draft for comparison. A backup is optional, never required. **Download master draft backup** retains the current original artwork, placements and permissions in JSON. Explicitly restoring that workspace backup (or an existing design ZIP) changes the local canvas only and reads the latest server revision; it requires review and a separate Save click. A changed revision during that review still fails safely. Saving and restoring do not publish.

`tests/team-visual-editor-browser.mjs` verifies direct authenticated loading without setup cache, original upload, owner canvas drag/resize, backgrounds/zones, replaced-name permission selection, optional backup recovery after a conflict, detached in-flight save snapshots, confirmed-save return/receipt, protection for further in-flight edits, saved placement/permission reopen, and independent customer text edits plus canvas movement on both Front and Back.


## Separate garment drafts under one team

Owner strict workspaces support `tshirt`, `long-sleeve-tshirt`, `short-sleeve-polo`, `long-sleeve-polo` and `fleece-hoodie`. The existing primary master stays in its original table/RPC; additional garment drafts have independent `(team_id, product_id)` revisions in a private table. The owner can explicitly copy a saved master revision into missing garment drafts. The action refuses existing destinations, preserves original artwork bytes and normalized placements, uses each destination’s existing model/templates, and refuses to discard artwork in unsupported zones. Selected name fields can become editable and movable in the copies. The source remains unchanged; every destination still needs visual review and an explicit final Save. Opening/saving a staged garment does not enable it for customers, change setup, publish, send mail or create payment. Owner setup and the studio link to each private garment draft, including staged garments not yet enabled. Optional copying uses only the server-saved source revision and records that provenance; it never reads an unsaved canvas. Save/reopen, explicit permissions and original artwork apply to each separately. Native navigation protection warns before discarding unsaved owner edits.

Enable desired garments in the owner setup and save it before publishing. The one explicit Publish action first confirms all enabled garments have saved masters, creates immutable versions, then publishes a snapshot containing the exact version ID per garment. The backend verifies all expected IDs and each garment mapping. A partial failure can create an immutable private version but cannot be reported as successful public activation. Reopen setup before retrying. The same customer team URL lists its enabled published garments; switching starts a separate personal copy and warns the member to save their current copy first. Old version references remain usable.

All-over 3D Teams polos use the existing regular 3D mapping and production templates for their zones; the chest-only rule still applies to 2D and other print methods. No template dimensions, model geometry, safe areas, seams, garment prices or subscription terms change. Long-sleeve polo uses the existing regular garment price schedule. Checkout remains disabled for owner design-review workspaces.

`tests/team-garment-drafts-browser.mjs` uses synthetic originals and intercepted API writes to exercise each garment's visual placement, separate saves/reopening, both member names editing/movement, explicit five-garment publication and actual ZIP creation. ZIP verification checks original bytes/measured dimensions, member text, font resources and every existing mapped zone's output dimensions. `tests/team-garment-master-database.sql` exercises the real new RPC in isolated PostgreSQL, including stale writes, independent versions, original primary compatibility, owner staging restrictions and denied public grants. These tests do not publish a real team or place any order.


## Owner-created Team organizer billing (October 25)

Owner setup now includes **Organizer subscription access**, off by default, and a reward target defaulting to five. Add the organizer email and explicitly enable billing access, then save. Share the authenticated `/team-owner.html?setupId=<workspace>&organizer=1` link yourself. No email, invitation, Stripe customer, checkout or charge is created by saving. The organizer uses their own verified account; a contact email alone does not grant access. Brand billing remains unavailable.

The organizer sees only subscription status and aggregate reward progress. They may explicitly accept the displayed $20/month terms, start Stripe Checkout, manage their payment method, or cancel renewal. No master, setup, publication, customer order details, batches or production ZIP access is granted. Authenticated organizer identity is bound atomically at signup, and the accepted reward target is preserved. A bound payer with a subscription retains cancellation/payment access even if new organizer enrollment is disabled. Changing a bound organizer or accepted reward target requires a separate migration/consent workflow, not a silent settings edit.

The first month costs $20. Five qualifying paid garments in that subscription period earn a single $20 credit on the next renewal; no stacking and no credit for free-preview purchases before subscription starts. Refunded, disputed and pending units do not qualify. Existing legacy subscriptions retain ten unless a separate approved terms change is made. Owner-created Teams store their accepted target independently. The immutable published masters, member copies and orders remain unchanged by enrollment.

Garment checkout before subscription enrollment continues under the explicit owner waiver. Once a subscription exists, new orders require current paid status; a failed/expired subscription cannot fall back to the old waiver. Review-only publication or unpublishing stops new checkout but does not cancel recurring billing. The existing Stripe subscription webhook controls paid status. No real order or subscription is used during QA.

Validation includes `tests/organizer-billing-browser.mjs`, actual-handler auth/enrollment/portal tests in `tests/owner-team-workspace.mjs`, the real invoice-created handler in `tests/team-service.mjs`, and service-only binding/free-to-paid database checks in `tests/owner-organizer-billing.sql`.


## Duplicate a saved team into a private draft

From an existing MQD owner workspace, choose **Duplicate team**, enter the new team name and unused link name, then **Create private copy**. Only the last saved setup and all saved garment drafts are copied; unsaved browser edits are not included. Open the returned private draft, replace its setup logo and artwork in each garment with the existing visual editor, save/reopen and preview, then explicitly publish when ready. Changing the setup logo does not automatically replace image layers inside strict masters.

The atomic copy retains garment choices, original inline artwork, backgrounds, placements and member rules, including movable names. It starts with new draft revisions, no published versions/link, no checkout waiver, blank organizer contacts/private request notes, organizer access off and the default reward target of five. No orders, Stripe identities, subscription terms, or production files are copied. The source team is unchanged. Same-request retries recover the created draft without resetting its edits. The server endpoint requires current MQD admin MFA; the database operation is service-role only.


## Customer checkout with large original artwork

Checkout keeps the existing 50 MiB ZIP and 51 MiB multipart limits. The server counts the multipart stream before native parsing, reads only account/publication fields needed for checkout, and compares protected designs directly without serializing two complete copies of inline artwork. Every existing master, print-zone, source-byte, font, order, payment and private-storage check still runs.

Customers see a persistent checkout progress dialog while artwork is prepared and sent, including on mobile when production capture switches preview panes. A failed request shows a clear recovery message and retains the design. Unchanged retries reuse the exact ZIP and request identifier; view state and export timestamps do not create a new attempt. A single mandatory all-over print method is hidden from the form.


Checkout transport also stores each identical original image once in the ZIP. The opt-in `mqd-team-image-refs-v1` envelope references originals from design.json; the server restores their exact bytes and MIME types before validating the protected member copy. The production manifest records their verified paths and hashes. Saved ZIP import restores those references too; ordinary customer backups retain their existing inline format. Comparison clones share immutable source strings while making independent object containers, avoiding large duplicate buffers. Historical inline packages continue to work.

The service-only `mqd_team_checkout_master` RPC returns the immutable master with SHA-256 fingerprints in place of inline source strings. Checkout hydrates those source strings exclusively from the submitted artwork after verifying its exact UTF-8 digest, then applies normal member-copy validation. The stored master is never changed, cross-team version lookup returns no result, and public/authenticated roles cannot execute this RPC. This avoids fetching another full copy of original artwork into the Edge runtime.

## Mobile loading and owner-only payment verification

The team 3D page shows loading progress before the designer modules load, with visible recovery if a module fails or the network is slow. Public master transport can request `compact=1` to send repeated original images once; the client restores the exact source strings before independent-copy validation. Published versions and production dimensions are unchanged.

An MQD admin with verified MFA can use `ownerTest=1` on the designer/API/admin/order-status pages to exercise the existing sandbox team and Stripe test credentials without changing global live mode. The API independently verifies fresh owner identity and MFA, forces sandbox configuration, and allows only order checkout/status and owner order inspection/download; publishing and administrative mutations are denied. Normal customers cannot activate this mode. Signed sandbox webhooks are verified against the separate sandbox secret even while live mode is active. Test-signed live events are rejected, and sandbox notifications stay suppressed.

### Public designer load performance

Compact owner-team reads use the service-only `mqd_read_owner_team_public` projection and private `mqd_team_public_read_cache`. Original image strings are deduplicated in Postgres, without resizing or altering immutable master rows. The cache is keyed by team, business revision and garment; current account mode/status/billing and business status are read on every request. A changed revision cannot reuse the previous packet. Historical explicit-version requests use the uncached team-scoped builder. No HTTP/public cache or new public table permissions are introduced. Cache misses rebuild from the authoritative publication; the first request after a changed revision can be slower. Old revision cache rows are discarded when a new packet is built.

Manual verification: `tests/team-public-read.sql` checks source/master equality and denial of direct anonymous/customer reads against the Mopar Kingz publication. `tests/team-service.mjs` covers accelerated-path publication/billing/garment denial; transport tests verify that pre-packed originals are never packed twice. The team HTML preloads the existing designer module while the team request is in flight, but evaluation still waits for validated shop settings.
