# Chat with MQD

Help now includes an asynchronous human conversation. Existing automated questions and design requests remain separate. Owner inbox: `/owner-chat.html`. Email opens `/owner/?chat=<conversation UUID>`; the approved owner completes existing Google sign-in and MFA, then returns to that conversation. The return target accepts only UUIDs and is stored in the same tab during OAuth.

Guest access uses a 256-bit random capability in a request header, never a URL. Only its SHA-256 hash is stored server-side. The tab keeps its credential and pending send ID in sessionStorage. Closing/forgetting the tab loses access; access expires after 30 days. This is stated in the UI. Owners retain access to archived records. Messages are text only, limited to 2000 characters and 500 per conversation. There are no attachments, AI actions, email replies, SMS or marketing.

Tables have RLS enabled and no anon/authenticated grants or policies. Service-only RPCs atomically save messages and notification records, reject conflicting retry IDs, lock conversations, advance read cursors monotonically and lease notifications. Edge code verifies guest capabilities or current `getUser` admin role plus verified AAL2 claims on every owner operation. Credentials and message bodies are never logged. The existing daily budget RPC enforces fail-closed IP, conversation, creation and global limits.

Notifications use the existing `MQD_RESEND_API_KEY`/`mqd_resend_api_key` and `MQD_EMAIL_FROM`/`mqd_email_from` configuration, with the same MQD default sender as design requests. Recipient `mqdrva@gmail.com` was verified against the existing design-request handler and current approved admin account. Email includes only a portal link and instructions, no message text or guest token. No provider/plan is activated by this feature.

Messages remain saved if notification delivery fails. Initial send, subsequent conversation reads, and owner retry process a persisted queue with leases and exponential backoff. Retries stop after five attempts or 23 hours and require provider review to avoid sending outside the idempotency window. There is no new background scheduler: if both parties close their tabs, pending retries resume on reopening the conversation. The inbox exposes pending/review state; customers see an honest pending-alert message. Provider acceptance is recorded, not a claim of inbox delivery.
